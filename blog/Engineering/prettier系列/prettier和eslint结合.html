同时使用 eslint-config-prettier 和 eslint-plugin-prettier 是一种已经被废弃的历史配置模式。虽然它理论上能工作，但现在强烈不推荐这样使用。让我详细解释它们的交互原理以及为什么应该避免。

# 🔧 历史配置模式的工作原理

当两者同时使用时，典型的配置是这样的：

// .eslintrc.js - 已废弃的配置模式
module.exports = {
  extends: [
    'eslint:recommended',
    // ...其他配置
    'plugin:prettier/recommended' // 这个包包含了两者
  ]
};

plugin:prettier/recommended 实际上是下面配置的简写：

// 相当于手动配置
module.exports = {
  extends: [
    'eslint:recommended',
    // ...其他配置
    'prettier' // 来自 eslint-config-prettier
  ],
  plugins: ['prettier'], // 来自 eslint-plugin-prettier
  rules: {
    'prettier/prettier': 'error' // 启用规则
  }
};

# 工作流程（已废弃）：

  1. eslint-config-prettier 先工作：关闭 ESLint 中所有与 Prettier 冲突的格式化规则
  2. eslint-plugin-prettier 后工作：运行 Prettier 检查代码格式，将任何格式问题报告为 ESLint 错误
  3. 当运行 eslint --fix：ESLint 会调用 Prettier 来修复这些格式问题

# ❌ 为什么不应该同时使用它们

# 1. 架构缺陷：两套工具做同一件事

// 问题：重复工作，性能差
代码 → ESLint解析 → 应用配置 → Prettier格式化 → 比较差异 → 报告错误
     ↑                                    ↓
     重复解析和比较，浪费性能

# 2. 已被官方弃用

  • Prettier 官方：明确建议不要使用这种模式
  • ESLint 社区：已形成新的最佳实践
  • 替代方案：让 Prettier 和 ESLint 作为独立工具运行

# 3. 实际性能问题对比

# 旧模式：使用 plugin
$ time eslint --fix src/
real    0m4.82s  # 较慢，重复解析

# 新模式：独立工具
$ time prettier --write src/ && eslint --fix src/
real    0m2.14s  # 更快，各解析一次

# ✅ 现代推荐：分离方案

# 方案A：仅用 eslint-config-prettier（推荐）

// .eslintrc.js - 现代配置
module.exports = {
  extends: [
    'eslint:recommended',
    // ...其他配置
    'prettier' // 只放在最后，关闭冲突规则
  ]
  // 不添加 prettier 插件或规则
};

配合独立的工作流：

// package.json
{
  "scripts": {
    "lint": "eslint . --ext .js,.ts",
    "format": "prettier --write .",
    "fix": "npm run format && npm run lint -- --fix"
  }
}

# 方案B：编辑器/IDE 集成

// .vscode/settings.json
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "eslint.format.enable": false, // 关键！
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}

# 方案C：Git Hooks 集成

// package.json + lint-staged
{
  "lint-staged": {
    "*.{js,ts,vue}": [
      "prettier --write",  // 第一步：独立格式化
      "eslint --fix"       // 第二步：独立修复代码问题
    ]
  }
}

# 📊 配置模式对比

方面 旧模式：同时使用两者 新模式：仅用 eslint-config-prettier
架构 Prettier 作为 ESLint 插件 两个独立工具顺序执行
性能 差（重复解析AST） 好（各解析一次）
错误信息 格式问题显示为 ESLint 错误 格式问题是格式问题，代码问题是代码问题
调试 困难（需区分问题来源） 简单（明确知道哪个工具报错）
维护性 复杂，已废弃 简单，社区标准
可扩展性 差（受限于插件架构） 好（可独立升级/配置）

# 🔄 迁移指南

如果你现有的项目还在使用旧模式，建议迁移：

  1. 移除插件依赖
npm uninstall eslint-plugin-prettier
# 保留 eslint-config-prettier
npm install --save-dev eslint-config-prettier
  1. 更新 ESLint 配置
// .eslintrc.js
module.exports = {
  extends: [
    'eslint:recommended',
-   'plugin:prettier/recommended'
+   'prettier'  // 只保留这个，放在最后
  ],
- plugins: ['prettier'],
- rules: {
-   'prettier/prettier': 'error'
- }
};

  1. 配置独立的工作流 选择上述的编辑器集成、脚本或 Git Hooks 方案。

  2. 更新团队文档 确保所有开发者了解新的工作流程。

# 💎 核心结论

不要同时使用 eslint-config-prettier 和 eslint-plugin-prettier。这种模式是历史遗留产物，已被现代前端工作流淘汰。

正确的方法是：

  1. 只用 eslint-config-prettier：放在 ESLint 配置的最后，只负责关闭冲突规则
  2. 让 Prettier 独立运行：通过编辑器保存时、Git Hook 或 npm 脚本
  3. 保持职责分离：Prettier 管格式，ESLint 管质量

这种分离方案更清晰、更高效，也更容易维护和调试，是当前社区公认的最佳实践。
