# 引言

很多开发者只是安装并使用了Prettier，并未真正理解其设计哲学，导致与ESLint、编辑器功能产生冲突，无法发挥最大效能。

本文主要介绍：

  • 常见的Prettier使用误区
  • 如何停止与eslint冲突
  • Prettier的正确使用和配置方式

# 几大误区

# 误区1：做什么和不做什么？

理解Prettier的关键在于 “专精” ：

  • 它只做一件事：代码格式化。它将你的代码重新排版，使其风格完全统一（空格、缩进、引号、换行等）。
  • 它不做另一件事：代码质量检查。它不关心变量是否未使用、函数是否过长、是否应该用 === 等问题。
  • 它是“独裁者”：它的规则几乎没有商量的余地。要么接受它所有的风格决策（通过配置），要么就别用。这反而成了它的优点——消灭所有风格争论。

大多数人“错误地使用”，本质上是 “混淆了Prettier和ESLint的职责”，让两者在“格式”这个领域打架。

# 误区2：不要依赖默认配置

很多开发者甚至没有创建 .prettierrc 文件。

这意味着他们在使用 Prettier 的全局默认配置，而这很可能与团队的编码风格不匹配。

在项目根目录创建 .prettierrc.yaml：

semi: true
singleQuote: true
tabWidth: 2
printWidth: 100
trailingComma: es5
arrowParens: always

# 误区3：不使用 .prettierignore

Prettier 默认会格式化所有文件。

包括构建产物、JSON 配置、自动生成文件，这些会显著拖慢格式化速度。

创建 .prettierignore：

out
dist
pnpm-lock.yaml
LICENSE.md
tsconfig.json
tsconfig.*.json
# ...

# 误区4：忽略 “Check Mode”

Prettier 的隐藏宝藏是 --check 选项。

  • --write：直接格式化文件
  • --check：只检查文件是否已符合格式
npx prettier --check .

非常适合用于 CI/CD 或 Git 提交钩子，可以防止未格式化的代码进入仓库。

配合 Husky + Lint-Staged：

{  
    "lint-staged": {
        "*.{js,ts,jsx,tsx,css,html,md}": "prettier --check"
    }
}

效果？

每次提交时，Prettier 会自动确保所有文件都符合格式规范。

# 误区5：未同步编辑器设置

如果你是 VS Code 用户，这点尤其重要。

即使安装了 Prettier，如果它不是默认 formatter，它也不会自动运行。

打开 VS Code 设置（JSON），添加：

{
  // 1. 为特定语言指定格式化器，避免冲突
  "[javascript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[typescript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[vue]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  // ... 其他语言

  // 2. 核心：开启保存时自动格式化（由Prettier执行）
  "editor.formatOnSave": true,

  // 3. 核心：关闭ESLint的格式化功能，防止它与Prettier重复工作
  "eslint.format.enable": false,

  // 4. 核心：开启保存时由ESLint执行代码操作（自动修复质量问题）
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },

  // 5. 可选：Prettier不需要全局安装，使用项目内版本
  "prettier.prettierPath": "./node_modules/prettier",
  // 可选：要求必须有配置文件才运行，避免意外
  "prettier.requireConfig": true
}

这样可以确保：

  • 只有 Prettier 负责格式化
  • 只有在有 .prettierrc 的项目中运行（避免误伤）
  • 保存时自动格式化

# 误区6：忽略换行符（Line Endings）

这是跨 Windows 与 macOS 团队最隐蔽的“痛点”。

不同系统使用不同的换行符（CRLF vs LF），导致 Git 出现大量“幽灵 diff”。

在 .prettierrc.yaml 中添加：

endOfLine: lf

在 .gitattributes 中设置：

* text eol=lf

从此 Git 不再出现莫名其妙的文件修改。

# 误区7：没有自动化格式化

如果你还在手动运行 Prettier，那就是在浪费时间。

在 package.json 中加入：

"scripts": {  
    "format": "prettier --write .",
    "check-format": "prettier --check ."
}

现在你可以运行：

npm run format
npm run check-format

配合 Husky 的 pre-commit hook，你甚至不需要思考格式化这件事。

# 正确使用方式

# 1.安装

npm install --save-dev prettier

# 2.创建 .prettierrc

(例如 .prettierrc.json)：定义你团队统一的风格

{
  "semi": false,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "es5"
}

# 3.创建 .prettierignore

忽略不需要格式化的文件（如 node_modules, dist）

out
dist
pnpm-lock.yaml
LICENSE.md
tsconfig.json
tsconfig.*.json

# 4.与eslint集成

仅使用 eslint-config-prettier，安装

npm install --save-dev eslint-config-prettier

// .eslintrc.js - 只需这一行
module.exports = {
  extends: [
    'eslint:recommended',
    // ... 其他配置
    'prettier' // 必须在最后！用于关闭所有冲突规则
  ]
};

有些文档会推荐安装 eslint-plugin-prettier。但请注意，这已不是主流推荐做法，因为它会让ESLint调用Prettier，有时反而增加复杂性。

# 5.配置编辑器（VSCode 自动化）

这是实现流畅体验的关键。配置VSCode，在保存时先运行Prettier格式化，再运行ESLint自动修复。

  1. 安装两个必备扩展：Prettier - Code formatter 和 ESLint。
  2. 配置 VSCode 设置 (settings.json)：

**注：**个人编辑器配置（settings.json）无法提交到仓库，必然导致“在我机器上能自动格式化，在你机器上就不行”的问题

# 6.将编辑器配置“项目化”

# 方案一：配置标准化 (最实用)

在项目根目录创建 .vscode/ 文件夹，并提交以下文件到版本控制，这样配置会自动应用到所有打开此项目的VSCode。

1. 创建 .vscode/settings.json 这是最关键的文件，它定义了本项目专用的VSCode设置，会覆盖用户的全局设置。

json

{
  // 针对本项目的Prettier & ESLint设置
  "[javascript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[typescript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[vue]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[json]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  // 核心自动化工作流
  "editor.formatOnSave": true,
  "eslint.format.enable": false,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  // 强制使用项目内的Prettier和ESLint，避免版本不一致
  "prettier.prettierPath": "./node_modules/prettier",
  "eslint.nodePath": "./node_modules/eslint",
  // 可选：要求必须配置文件才运行，避免意外格式化
  "prettier.requireConfig": true,
  // 可选：关闭可能与Prettier冲突的VSCode内置格式化器
  "javascript.format.enable": false,
  "typescript.format.enable": false
}

2. 创建 .vscode/extensions.json (推荐) 此文件可以推荐（或强烈建议）开发者安装必要的扩展。当新成员打开项目时，VSCode会提示他们安装。

json

{
  "recommendations": [
    "esbenp.prettier-vscode",
    "dbaeumer.vscode-eslint"
    // 可以添加其他项目相关的扩展，如Vue、React等
  ]
}

注意：这只是一个友好的提示，并非强制安装。但团队规范中应要求安装。

# 方案二：严格方案 - 强制检查 (最可靠)

作为兜底方案，在Git提交或CI/CD流水线中设立检查，确保提交的代码符合规范，无论开发者本地编辑器如何配置。

1. 配置 package.json 脚本

json

{
  "scripts": {
    "lint": "eslint . --ext .js,.ts,.vue --fix",
    "format": "prettier --write .",
    "pre-commit-check": "npm run lint && npm run format",
    "ci-check": "eslint . --ext .js,.ts,.vue && prettier --check ."
  }
}
  • pre-commit-check: 本地提交前运行，自动修复问题。
  • ci-check: 在CI（如GitHub Actions）中运行，只检查不修复，如果失败则阻塞合并。

2. 使用 Git Hooks 工具（如 Husky + lint-staged） 这是业界标准做法，确保提交到暂存区的代码都是规范化的。

bash

# 安装
npm install --save-dev husky lint-staged

json

// package.json 配置
{
  "lint-staged": {
    "*.{js,ts,vue}": [
      "prettier --write",
      "eslint --fix"
    ],
    "*.{json,md}": [
      "prettier --write"
    ]
  }
}

配置后，每次 git commit 时，lint-staged 都会自动对本次提交的文件运行Prettier和ESLint修复。
